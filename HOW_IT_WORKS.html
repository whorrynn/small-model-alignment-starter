The one-sentence version of the whole assignment: take a small pretrained language model, teach it to follow instructions (SFT), then teach it to prefer better answers over worse ones (DPO), and prove it got better using a third AI model as a judge.

Each section below first explains the idea, then walks through the literal code, line by line, in a bulleted list: the code in `code span` form, followed by what that exact line does and why.

Part 0: The shared vocabulary

A few terms get used constantly below. If you already know them, skip ahead.

  • Tokenizer: converts text into a list of integers ("tokens") the model actually operates on, and back again. "Hi there" might become [9906, 1070].
  • Logits: the model's raw, un-normalized output scores for "what's the next token", one score per vocabulary entry, at every position in the sequence. Shape: (batch, sequence_length, vocab_size).
  • Log-probability (logprob): log(probability). We work in log-space almost everywhere because multiplying many small probabilities together underflows to zero on a computer, but adding their logs doesn't.
  • Causal LM: the model predicts each token using only the tokens that came before it (left-to-right), never tokens after it. This is why "the logits at position t predict the token at position t+1" shows up constantly in the code.
  • Gradient / backward pass / .backward(): how PyTorch computes "if I nudge each model weight slightly, does the loss go up or down." Calling .backward() on a loss tensor computes this for every weight that contributed to it. torch.no_grad() turns this bookkeeping off for a block of code — used whenever we score something but don't want to train on it.
  • Checkpoint: a saved snapshot of the model's weights at some point in training, so you can reload it later without retraining.
  • -100 label convention: PyTorch's cross-entropy loss treats any label equal to -100 as "skip this position." This shows up constantly as the mechanism for "only train on response tokens."

Part 1: src/prompt_format.py — the one shared template

The idea: every piece of code that touches a prompt has to format it identically, or comparisons between models stop being fair. Putting the template in exactly one function and importing it everywhere makes it structurally impossible for two parts of the pipeline to disagree.

The code, line by line:

from __future__ import annotations


def format_prompt(instruction: str, tokenizer=None) -> str:
    return f"Instruction:\n{instruction}\n\nResponse:\n"
  • from __future__ import annotations — makes type hints (like str | Path used elsewhere in this project) evaluate lazily as strings rather than being executed immediately. Without this, type hints written in the modern X | Y union syntax would crash on Python versions older than 3.10 the moment the file is imported, even if you never actually use the hint. This import appears at the top of nearly every file in this project for that reason — it's not specific to this file.
  • def format_prompt(instruction: str, tokenizer=None) -> str: — the function signature. tokenizer is accepted but deliberately unused here; it's in the signature so every call site can pass it uniformly (some alternate template designs, like a real chat template, would need the tokenizer — keeping the parameter means callers don't need to change if the template design changes later).
  • return f"Instruction:\n{instruction}\n\nResponse:\n" — the entire template. An f-string that embeds the raw instruction between two labeled sections, ending with "Response:\n" so the very next tokens the model sees/generates are the response itself. The blank line (\n\n) between the instruction and the Response: label gives the model a visually distinct section break, the same way a human-written document would.

Part 2: src/batching.py — turning text into trainable tensors

The idea: given prompts and responses, produce three tensors a model can train on — input_ids (what it reads), attention_mask (what's real vs. padding), and labels (what it's graded on, with prompt/padding positions blanked out via -100).

The code, line by line:

from __future__ import annotations

def build_sft_batch_impl(tokenizer, prompts, responses, max_length):

  • def build_sft_batch_impl(tokenizer, prompts, responses, max_length): — takes a tokenizer, parallel lists of prompt/response strings, and the truncation cap.
  • eosId = tokenizer.eos_token_id — the integer ID of the end-of-sequence token, read once up front instead of re-reading it inside the loop below.
  • padId = tokenizer.pad_token_id if tokenizer.pad_token_id is not None else eosId — most tokenizers have a dedicated pad token, but some (historically, GPT-2-style tokenizers) don't define one. If pad_token_id is None, fall back to using the EOS token as padding instead of crashing later when we try to build a padding tensor with a None fill value.
    rowIds, rowLabels = [], []
    for prompt, response in zip(prompts, responses):
        promptIds = tokenizer.encode(prompt, add_special_tokens = False)
        responseIds = tokenizer.encode(response, add_special_tokens = False)
        if eosId is not None:
            responseIds = responseIds + [eosId]
  • rowIds, rowLabels = [], [] — two parallel accumulator lists; one entry per example, filled in by the loop below, before any padding happens (padding happens once, after every row's natural length is known).
  • for prompt, response in zip(prompts, responses): — iterate the two parallel input lists together, one (prompt, response) pair per iteration.
  • promptIds = tokenizer.encode(prompt, add_special_tokens = False) — tokenize just the prompt half. add_special_tokens = False means "don't automatically add a beginning/end-of-sequence token here" — we want full manual control over exactly where EOS goes (see the next few lines), rather than the tokenizer silently inserting one wherever its default convention says to.
  • responseIds = tokenizer.encode(response, add_special_tokens = False) — same, for the response half. Kept as a separate list from promptIds specifically so we still know the exact boundary between "prompt" and "response" after they get concatenated two lines down.
  • if eosId is not None: — guard against a tokenizer that has no EOS token defined at all (rare, but possible).
  • responseIds = responseIds + [eosId] — append the EOS token id to the response only, never the prompt. This is what teaches the trained model to stop generating instead of rambling forever.
        fullIds = (promptIds + responseIds)[:max_length]
        promptLen = min(len(promptIds), len(fullIds))  # clip in case the prompt alone overflows
  • fullIds = (promptIds + responseIds)[:max_length] — concatenate prompt tokens followed by response tokens (prompt first — this is a causal LM, so the model reads left to right, and the prompt must come before the response it's conditioned on), then truncate the whole thing to max_length. If the response is long enough that truncation lands before its end, the trailing EOS we just appended gets cut off along with it — this is the documented, acceptable behavior from the manual's "Expected behavior" list.
  • promptLen = min(len(promptIds), len(fullIds)) — normally len(promptIds) is what we want to call "how many tokens at the start of fullIds belong to the prompt." But in the edge case where the prompt by itself is already longer than max_length, fullIds got truncated down to something shorter than promptIds, so blindly using len(promptIds) would try to mask more positions than actually exist in the row. Taking the min of the two clips promptLen to never exceed the row's real length.
        labels = list(fullIds)
        labels[:promptLen] = [-100] * promptLen

        rowIds.append(fullIds)
        rowLabels.append(labels)
  • labels = list(fullIds) — start labels as an exact copy of the token sequence (so unmasked positions naturally equal the real token id, which is what cross-entropy needs to score "did the model predict this exact token").
  • labels[:promptLen] = [-100] * promptLen — overwrite the first promptLen entries (the prompt portion) with -100, Python's slice assignment replacing that whole stretch in one statement. This is the "response-only loss masking" the manual asks for, implemented as data rather than as special-cased loss code.
  • rowIds.append(fullIds) / rowLabels.append(labels) — stash this row's finished (but not-yet-padded) sequences into the per-batch accumulators declared above the loop.
    seqLen = max(len(ids) for ids in rowIds)
    batchSize = len(rowIds)
  • seqLen = max(len(ids) for ids in rowIds) — once every row in the batch has been processed, find the single longest row — that's the width every row gets padded to. (Guaranteed <= max_length since every row was already truncated to that cap above.)
  • batchSize = len(rowIds) — just the row count, used to size the output tensors next.
    inputIds = torch.full((batchSize, seqLen), padId, dtype = torch.long)
    attentionMask = torch.zeros((batchSize, seqLen), dtype = torch.long)
    labelsTensor = torch.full((batchSize, seqLen), -100, dtype = torch.long)
  • inputIds = torch.full((batchSize, seqLen), padId, dtype = torch.long) — allocate the full (batchSize, seqLen) output tensor pre-filled with the pad token id everywhere. Real tokens get written over this in the loop below; anything never written stays as padding.
  • attentionMask = torch.zeros((batchSize, seqLen), dtype = torch.long) — same shape, pre-filled with 0 (meaning "ignore this position"). Real tokens get flipped to 1 below.
  • labelsTensor = torch.full((batchSize, seqLen), -100, dtype = torch.long) — same shape again, pre-filled with -100. This is the critical detail: padding positions are never overwritten for this tensor (only the real per-row labels content gets written in below, up to each row's own length), so padding automatically stays -100 — i.e., ignored by the loss — without any extra code to special-case it.
    for row, (ids, labels) in enumerate(zip(rowIds, rowLabels)):
        length = len(ids)
        inputIds[row, :length] = torch.tensor(ids, dtype = torch.long)
        attentionMask[row, :length] = 1
        labelsTensor[row, :length] = torch.tensor(labels, dtype = torch.long)
  • for row, (ids, labels) in enumerate(zip(rowIds, rowLabels)): — walk the two per-row lists together, with row as the index into the output tensors.
  • length = len(ids) — this specific row's real (unpadded) length.
  • inputIds[row, :length] = torch.tensor(ids, dtype = torch.long) — write this row's real token ids into the first length columns of the pre-allocated tensor; everything from length onward in that row keeps the padId it was initialized with.
  • attentionMask[row, :length] = 1 — mark exactly those same length positions as "real" (everything after stays 0).
  • labelsTensor[row, :length] = torch.tensor(labels, dtype = torch.long) — write this row's labels (which already has -100 baked in for its own prompt portion) into the first length columns; positions past length keep the tensor's -100 fill value — this is the padding-masking.
    return {"input_ids": inputIds, "attention_mask": attentionMask, "labels": labelsTensor}
  • Returns exactly the three required keys, matching the contract every caller (and the public test suite) expects.
def build_dpo_batch_impl(tokenizer, prompts, chosen_responses, rejected_responses, max_length):
    return {
        "chosen": build_sft_batch_impl(tokenizer, prompts, chosen_responses, max_length),
        "rejected": build_sft_batch_impl(tokenizer, prompts, rejected_responses, max_length),
    }
  • The entire DPO batch builder is a two-key dict, each value produced by calling the exact same build_sft_batch_impl above — once against the chosen responses, once against the rejected ones, both times with the same prompts list. There is no new tensor logic here at all: reusing the SFT builder is what guarantees the prompt is tokenized identically on both sides, so only the response differs between "chosen" and "rejected."

Part 3: src/logprobs.py — "how likely was this response, according to the model?"

The idea: given a model and (prompt, response) pairs, return one number per example — the total log-probability the model assigns to the response tokens only.

The code, line by line:

from __future__ import annotations

import torch
import torch.nn.functional as F

from src.batching import build_sft_batch_impl
  • import torch — for .to(device), tensor ops.
  • import torch.nn.functional as F — specifically for F.log_softmax below; F is the conventional alias for this module everywhere in PyTorch code.
  • from src.batching import build_sft_batch_impl — reuses the exact same batch-building logic from Part 2 rather than re-tokenizing by hand here.
def compute_response_logprobs_impl(model, tokenizer, prompts, responses, max_length):
    batch = build_sft_batch_impl(tokenizer, prompts, responses, max_length)
    device = next(model.parameters()).device
    inputIds = batch["input_ids"].to(device)
    attentionMask = batch["attention_mask"].to(device)
    labels = batch["labels"].to(device)
  • batch = build_sft_batch_impl(...) — get the padded/masked tensors for this (prompts, responses) pair, exactly as SFT training would.
  • device = next(model.parameters()).device — ask the model itself which device it currently lives on (CPU, cuda:0, cuda:1, ...) by peeking at its first parameter tensor, rather than requiring the caller to pass a device explicitly. This is what lets this one function correctly score the policy model and the reference model even when they live on two different GPUs.
  • inputIds = batch["input_ids"].to(device) — build_sft_batch_impl always builds tensors on the CPU (there's no device argument anywhere in Part 2); this line is what actually moves them onto whichever device the model needs.
  • attentionMask = batch["attention_mask"].to(device) / labels = batch["labels"].to(device) — same move, for the other two tensors.
    logits = model(input_ids = inputIds, attention_mask = attentionMask).logits
  • Runs the actual forward pass. model(...) on a Hugging Face causal LM returns an object with several fields; .logits pulls out the raw, pre-softmax prediction scores, shape (batch, sequence_length, vocab_size). Note labels is deliberately not passed into the model call here — if it were, the HF model would compute its own internal loss using its own masking convention, which we don't want; we compute the loss ourselves, by hand, in the lines below.
    # Causal-LM shift: logits[:, t] predicts the token at position t + 1.
    shiftLogits = logits[:, :-1, :]
    shiftLabels = labels[:, 1:]
  • shiftLogits = logits[:, :-1, :] — drop the logits at the very last sequence position (there's no "next token" to predict there, since the sequence ends). Keeps all batch rows (:) and the full vocab dimension (:), drops only the last position along the sequence axis.
  • shiftLabels = labels[:, 1:] — drop the label at the very first position instead. The effect: shiftLogits[:, t] and shiftLabels[:, t] now refer to the same real token — the logits that predicted it, lined up against the token that actually came next. This one-position misalignment is exactly what "causal LM shift" means.
    logProbs = F.log_softmax(shiftLogits, dim = -1)
    responseMask = shiftLabels.ne(-100)
    safeLabels = shiftLabels.clamp_min(0)  # -100 is not a valid gather index
    tokenLogProbs = logProbs.gather(dim = -1, index = safeLabels.unsqueeze(-1)).squeeze(-1)
    tokenLogProbs = tokenLogProbs * responseMask
  • logProbs = F.log_softmax(shiftLogits, dim = -1) — convert raw logits into log-probabilities over the vocabulary (last dimension, dim = -1). log_softmax is used instead of softmax followed by .log() because it's numerically stable — computing them separately can lose precision or even produce -inf for very small probabilities.
  • responseMask = shiftLabels.ne(-100) — a boolean tensor, True wherever the (shifted) label is a real response token, False wherever it's -100 (prompt or padding, from build_sft_batch_impl). .ne is "not equal."
  • safeLabels = shiftLabels.clamp_min(0) — .gather (next line) is going to use shiftLabels as an index into the vocabulary dimension, and a negative index like -100 isn't a valid position there — it would either error or silently index from the wrong end. Clamping every value to a minimum of 0 turns every -100 into a harmless 0 (pointing at some arbitrary real vocabulary entry). This is fine only because the very next line immediately zeroes out exactly those same positions via responseMask — the clamped value is never actually trusted, just computed so the indexing operation doesn't crash.
  • tokenLogProbs = logProbs.gather(dim = -1, index = safeLabels.unsqueeze(-1)).squeeze(-1) — .gather is "look up, for each position, the one entry in the vocabulary dimension specified by the index" — i.e., "what log-probability did the model assign to the token that actually appeared here." .unsqueeze(-1) adds a size-1 dimension so the index tensor's shape matches what .gather expects (it needs the same number of dimensions as logProbs); .squeeze(-1) removes that extra dimension again afterward, leaving tokenLogProbs with shape (batch, sequence_length - 1) — one log-probability per token position.
  • tokenLogProbs = tokenLogProbs * responseMask — multiply by the boolean mask (treated as 0/1): every prompt or padding position becomes exactly 0.0 (contributing nothing to the sum below); every real response position keeps its real log-probability value.
    return tokenLogProbs.sum(dim = -1)
  • Sum across the sequence dimension, collapsing (batch, sequence_length - 1) down to (batch,) — one summed log-probability per example, the function's documented return shape.

sft_loss_impl

def sft_loss_impl(model, tokenizer, prompts, responses, max_length):
    responseLogps = compute_response_logprobs_impl(model, tokenizer, prompts, responses, max_length)
    return -responseLogps.mean()
  • responseLogps = compute_response_logprobs_impl(...) — one summed response log-probability per example in the batch, straight from Part 3.
  • return -responseLogps.mean() — average those per-example log-probabilities across the batch, then negate. Averaging (rather than summing) keeps the loss magnitude independent of batch size — a batch of 2 and a batch of 32 produce losses on the same scale, which matters because the gradient-accumulation math in the training loops (Part 9/11) assumes that. Negating turns "maximize log-probability" (what we want) into "minimize this value" (what an optimizer does by default).

dpo_loss_from_logps_impl

def dpo_loss_from_logps_impl(
    policy_chosen_logps,
    policy_rejected_logps,
    reference_chosen_logps,
    reference_rejected_logps,
    beta,
):
    deltaTheta = policy_chosen_logps - policy_rejected_logps
    deltaRef = reference_chosen_logps - reference_rejected_logps
    perExampleLoss = -F.logsigmoid(beta * (deltaTheta - deltaRef))
    return perExampleLoss.mean()
  • deltaTheta = policy_chosen_logps - policy_rejected_logps — per example, how much more the trainable policy currently likes the chosen response than the rejected one (manual's Δθ, Eq. 3). Can be negative if the policy currently prefers the "wrong" (rejected) response.
  • deltaRef = reference_chosen_logps - reference_rejected_logps — the same gap, but measured under the frozen reference model (Δref, Eq. 4) — "how much did the model already prefer the chosen response, before any DPO training happened."
  • perExampleLoss = -F.logsigmoid(beta * (deltaTheta - deltaRef)) — the full DPO loss formula (Eq. 5) in one line. deltaTheta - deltaRef is "how much extra preference did DPO training add, beyond what the reference model already had." Multiplying by beta scales how sharply that gets pushed through the sigmoid. F.logsigmoid(x) computes log(sigmoid(x)) in one numerically stable operation (avoiding the separate-steps version, which can lose precision for large-magnitude x). Negating turns the "make this probability close to 1" training signal into something an optimizer can minimize.
  • return perExampleLoss.mean() — batch-mean, same reasoning as the SFT loss above (scale-independence of batch size).

  • with torch.no_grad(): — opens a block where PyTorch does not build a computation graph for anything inside it. Everything indented under this line runs, but produces tensors that .backward() can never trace back through.
  • referenceChosenLogps = compute_response_logprobs_impl(reference_model, ...) — score the chosen responses under the frozen reference model, inside the no-grad block.
  • referenceRejectedLogps = compute_response_logprobs_impl(reference_model, ...) — same, for the rejected responses. Because both of these calls are inside torch.no_grad(), there is no graph edge connecting reference_model's parameters to anything that gets .backward()'d later — it's structurally impossible for the reference model to receive a gradient from this function, regardless of what happens downstream.
    # Policy and reference may live on different devices (manual's Kaggle
    # memory tip: policy on cuda:0, frozen reference on cuda:1).
    referenceChosenLogps = referenceChosenLogps.to(policyChosenLogps.device)
    referenceRejectedLogps = referenceRejectedLogps.to(policyRejectedLogps.device)
  • Both lines move the reference-model tensors onto whatever device the policy-model tensors are already on. Necessary because compute_response_logprobs_impl (Part 3) places its output on whatever device the model it was given lives on — if policy_model is on cuda:0 and reference_model is on cuda:1, the four logprob tensors would otherwise be split across two devices, and the subtraction inside dpo_loss_from_logps_impl below would raise a "tensors on different devices" error.
    return dpo_loss_from_logps_impl(
        policyChosenLogps, policyRejectedLogps, referenceChosenLogps, referenceRejectedLogps, beta
    )
  • Hands all four (now same-device) logprob tensors, plus beta, to the pure-tensor loss function above. All the "talk to actual models" work is done by this point; the rest is just the formula.

implicit_rewards

def implicit_rewards(policy_logps, reference_logps, beta):
    return beta * (policy_logps - reference_logps)
  • One line, directly implementing manual Eq. 7/8: the implicit reward for a response is beta times how much more likely the policy makes it than the reference did. Works elementwise on tensors of any matching shape — called once for chosen responses and once for rejected responses by the DPO training loops (Parts 9/11).

reward_accuracy_and_margin

def reward_accuracy_and_margin(chosen_rewards, rejected_rewards):
    accuracy = (chosen_rewards > rejected_rewards).float().mean().item()
    margin = (chosen_rewards - rejected_rewards).mean().item()
    return accuracy, margin
  • accuracy = (chosen_rewards > rejected_rewards).float().mean().item() — chosen_rewards > rejected_rewards is an elementwise, strict greater-than comparison producing a boolean tensor (one entry per validation pair). .float() turns True/False into 1.0/0.0 so .mean() can average them into "fraction of pairs where chosen scored strictly higher" — exactly "accuracy." .item() pulls the single number out of its 0-dimensional tensor as a plain Python float (so it can be JSON-serialized by append_jsonl later, compared with Python's </> in BestCheckpointTracker, etc. — tensors don't support that as cleanly as plain floats).
  • margin = (chosen_rewards - rejected_rewards).mean().item() — the raw elementwise difference, averaged, then unwrapped the same way. Unlike accuracy, this isn't thresholded — a pair where chosen barely edges out rejected and a pair where chosen crushes rejected both count as "correct" for accuracy, but contribute very differently to the margin. The strict > in the accuracy line (not >=) is what makes a perfectly tied (untrained, policy == reference) model score accuracy 0, matching the manual's Section 10.5 callout.

_cosine_warmup_lambda — the learning-rate schedule, as a function

def _cosine_warmup_lambda(step: int, total_steps: int, warmup_steps: int) -> float:
    if step < warmup_steps:
        return step / max(1, warmup_steps)
    progress = (step - warmup_steps) / max(1, total_steps - warmup_steps)
    return 0.5 * (1.0 + math.cos(math.pi * min(1.0, progress)))
  • if step < warmup_steps: return step / max(1, warmup_steps) — during the warmup phase, the multiplier ramps linearly from 0 (at step = 0) up to 1 (at step = warmup_steps). max(1, warmup_steps) avoids a division by zero in the degenerate case where warmup is configured to 0 steps.
  • progress = (step - warmup_steps) / max(1, total_steps - warmup_steps) — after warmup, compute "how far through the post-warmup portion of training are we," as a fraction from 0 to 1. Same zero-division guard.
  • return 0.5 * (1.0 + math.cos(math.pi * min(1.0, progress))) — the cosine decay formula: at progress = 0 this is 0.5 * (1 + cos(0)) = 0.5 * 2 = 1.0 (full learning rate right after warmup); at progress = 1 it's 0.5 * (1 + cos(π)) = 0.5 * 0 = 0.0 (learning rate decayed to zero by the end of training). min(1.0, progress) clamps in case this function is ever called with step slightly past total_steps, so the multiplier never goes negative.
  • This function is never called directly in the training loop — it's handed to torch.optim.lr_scheduler.LambdaLR a few lines down, which calls it once per optimizer step automatically.

def _evaluate_sft_loss(model, tokenizer, prompts, responses, config, batch_size = 8):
    wasTraining = model.training
    model.eval()

    totalLoss, totalBatches = 0.0, 0
    with torch.no_grad():
        for start in range(0, len(prompts), batch_size):
            batchPrompts = prompts[start:start + batch_size]
            batchResponses = responses[start:start + batch_size]
            if not batchPrompts:
                continue
            loss = sft_loss_impl(model, tokenizer, batchPrompts, batchResponses, config.context_length)

            totalBatches += 1

    model.train(wasTraining)
    return totalLoss / max(1, totalBatches)

  • totalLoss, totalBatches = 0.0, 0 — running sum of per-batch losses and a count of how many batches contributed, so an average can be computed at the end.
  • with torch.no_grad(): — validation doesn't train anything, so no gradient tracking is needed (saves memory/time, same reasoning as generation).
  • for start in range(0, len(prompts), batch_size): — walk the validation set in fixed-size chunks, same chunking pattern as generate_responses.

def set_seed(seed: int) -> None:

def append_jsonl(path: str | Path, record: dict) -> None:
    path = Path(path)
    path.parent.mkdir(parents=True, exist_ok=True)
    with open(path, "a", encoding="utf-8") as handle:
        handle.write(json.dumps(record) + "\n")

def read_jsonl(path: str | Path) -> list[dict]:
    path = Path(path)
    if not path.exists():
        return []
    with open(path, encoding="utf-8") as handle:
        return [json.loads(line) for line in handle if line.strip()]
  • path = Path(path) — normalize.

  • else: unknown += 1 — a defensive catch-all for any judgment that doesn't fit either bucket (e.g., dpoModelName itself came back None because no judged record's models matched the naming convention at all) — rather than crashing or silently mis-counting, these get their own explicit bucket.
  • return {"wins": ..., "losses": ..., "ties": ..., "unknown": ..., "failures": len(failureRecords)} — the final summary dict, with "failures" simply being the count of records in the failures file.

Part 17: What's still genuinely untestable without Kaggle

Everything in Parts 0–5 and 13 (the pure math and I/O-only logic — batching, logprobs, losses, checkpoint.is_better, pairwise) is verified by the public test suite and by direct smoke-testing against a real (tiny) Hugging Face model — generation, the SFT loss/backward/optimizer step, and the DPO loss with correct gradient isolation between policy and reference all run correctly end-to-end on this machine.

What can't be fully exercised outside Kaggle: the actual dataset loads in data_sft.py / data_dpo.py / alpaca_eval_subset.py (this machine's datasets library can't even import — a Windows Application Control policy blocks a native pyarrow component it depends on; this is a restriction of this specific sandbox, not of the code, and won't apply on Kaggle's Linux environment), a full 30k-example SFT run or 15k-pair DPO run end to end (needs real GPU time), the LoRA/TRL run (needs the trl/peft packages — both are in requirements.txt), and the judging step (needs the Kaggle-only kaggle_benchmarks model-proxy). All of that code is written and internally consistent, but by its nature it needs Kaggle's environment to actually prove itself against real data and a real GPU — which is exactly what the smoke-test task referenced in Part 12/14's caveats was launched to do.
